BrineTank Telemetry Pipeline

A water-softener salt monitor: ultrasonic readings flow from a Raspberry Pi through IoT Core into a chain of Lambda functions that compute tank level, hold alert state, and email someone before the brine tank runs dry. A second, read-only stack in this same repo now lets customers check that level themselves; a separate storefront repo shares the brand but not the code — both below.

What it does

A Raspberry Pi with an ultrasonic distance sensor sits above each brine tank and publishes a reading — distance to the salt surface, an optional temperature, a status code — over MQTT every so often. AWS IoT Core catches every message on pi/+/telemetry and hands it to a Lambda that converts distance into a fill percentage, using two calibration points: the distance reading at empty (EMPTY_DISTANCE, 70 cm) and at full (FULL_DISTANCE, 6 cm).

Every reading is written to a rolling history table (45-day TTL) and a single “latest” row per device, then handed asynchronously to a second Lambda that owns alerting. That function is a small state machine: it only emails on the transition into a low state, respects a cooldown so it doesn't nag, and uses hysteresis so a level bouncing around the threshold doesn't flap between alert and all-clear. A separate check watches for a sudden jump from very-low to well-above-half, treats that as “someone poured in salt,” and fires a recovery email immediately.

Neither Lambda calls SES directly. Both alert types are dropped onto an SQS queue, and a third, single-purpose Lambda drains it in batches and is the only thing in the system allowed to send mail — failed sends retry up to three times before landing in a dead-letter queue instead of vanishing.

Components

Nine pieces, three of them Lambda functions, wired by IAM grants defined alongside them in the stack.

DEV

Sensor node

Raspberry Pi reading an A02YYUW ultrasonic sensor; publishes JSON — distance, filtered distance, temperature, status — over MQTT.

IOT

IoT Core rule

BrineTankIngestRule selects off pi/+/telemetry and invokes the ingest function directly — no broker code in between.

λ1

BrineTankIngest

30s timeout. Converts distance to percent_full against calibrated empty/full points, writes both tables, invokes the alert function async.

DB1

Readings / Latest tables

Pay-per-request DynamoDB. History keyed device+ts with a 45-day ttl_epoch; latest keyed device only, no expiry.

λ2

LowLevelAlert

10s timeout. Threshold + hysteresis + cooldown state machine, plus a salt-refill jump detector; the only writer of alert state.

DB2

SensorNotificationConfig

Per-sensor thresholds, hysteresis, cooldown, and the last known state — keyed on sensorId, read and written every invocation.

MQ

Email queue + DLQ

Decouples the decision to alert from actually sending mail. 3 retries at 30s visibility, then 14 days parked in a dead-letter queue.

λ3

EmailSender

30s timeout, batch size 10, partial-batch-failure reporting. The only function in the stack holding an ses:SendEmail grant.

SES

Amazon SES

Plain-text delivery from a verified sender identity (alerts@salty-water.com) to the addresses configured per sensor.

Why it doesn't spam you

Not to scale — the hysteresis band is 2 points wide by default, the diagram widens it so the mechanism is legible.

A drop below thresholdPercent (10%) fires one alert on the transition into LOW — not on every low reading — and won't fire again until cooldownSeconds (6h default) has passed. Recovery only registers once the level clears threshold + hysteresisPercent, so a level oscillating right at 10% can't trigger a new email every reading.

The customer portal: a second stack, same repo

A read-only consumer sits next to the pipeline above, not inside it. It imports the two data tables by name and only ever calls GetItem/Query — the accent-colored arrow below is the one line in the whole system that makes that a guarantee, not a convention.

A customer's browser is a small React SPA served from S3 behind CloudFront at portal.salty-water.com — an ACM certificate (us-east-1, DNS-validated) and a Route53 alias in the salty-water.com zone put it on a subdomain of the storefront, and the SPA now borrows that site's palette and typefaces so the two read as one brand. The bucket has no public access, only CloudFront can read it. Signing in is a direct Cognito SRP exchange, no hosted-UI redirect; the pool requires and verifies email before it will ever issue a token, because that email is also the partition key linking a customer to their device in a new, portal-owned table, CustomerDevices. Linking is still manual today — an aws dynamodb put-item call, the same shape as the existing sensor_email_map pattern above.

Every request into the API carries that Cognito JWT; a single Lambda checks CustomerDevices to confirm the caller actually owns the requested sensorId before it ever reads a reading — a 403 if not, never a silent scope to “whatever the path says.” Once ownership is confirmed, it reads BrineTankLatest and BrineTankReadings exactly as the pipeline stack left them: imported by table name, not by construct, so the two stacks share no CloudFormation export and can be destroyed independently. The HTTP API's CORS policy is an explicit origin allowlist — the portal's own domain plus localhost:5173 for local development — not the * it started as.

The other repo: SaltyWater storefront

A second, independent CDK stack — .vscode/SaltyWater — runs the customer-facing ordering site under the same domain. It does not share code, tables, or a stack with the pipeline above.

Customers hit a static site on S3 behind CloudFront (salty-water.com and saltydogsoftwater.com) to browse Crystal/Pellet salt and place an order. The order form posts to API Gateway, which routes to one of three Lambdas: Order Handler checks the zip code against a service-area table, writes the order, and publishes to SNS; anyone outside the delivery area gets logged to a leads table instead. Contact Handler stores inbound messages. An Amazon Pay Handler exists but is still a stub — no merchant credentials wired in yet. There's no email-sending Lambda here at all: SNS delivers the new-order notification straight to adam.lott@gmail.com.

There's also a third, much smaller IoT artifact in that repo: SaltSensor/main.py, MicroPython for a Raspberry Pi Pico W. It's a Wi-Fi-config captive portal plus a status page reporting uptime and board temperature — a prototype for a second kind of sensor, not the Pi + ultrasonic sensor this pipeline actually runs on, and it doesn't write to any table on either side.
