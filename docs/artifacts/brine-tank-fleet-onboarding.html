Onboarding a New Brine Tank Sensor

Today, adding a device means re-clicking through the AWS console from memory and hand-copying certificate files onto the Pi over SSH. This runbook replaces that with AWS IoT's fleet provisioning by trusted user — a workflow built for exactly your situation, one person commissioning devices one at a time. Set the pieces below up once; after that, onboarding a device is one command from your laptop.

Overview

Three ways AWS IoT Core lets you get a certificate onto a device. Only one fits how you actually work.

MethodFits when...Fits you?
Manual (console) One-off device, nothing worth automating What you're doing now — not repeatable
Provisioning by claim Devices are manufactured with a shared secret baked in before shipping Overkill — you're not manufacturing anything
Provisioning by trusted user One person commissions each device by hand at install time This is you

The trusted-user model splits the work into a one-time setup (the AWS-side resources that describe "how a brine tank sensor gets provisioned") and a per-device step you'll run every time you add a Pi. A short-lived claim certificate — good for five minutes — is the only credential that ever leaves your laptop; the device never holds any AWS IAM credentials, only its own final X.509 certificate.

Do once

1One-time setup

These resources describe the fleet, not any individual device. Set them up once (or fold them into your CDK stack — see the appendix) and every future device reuses them.

1.1 — Thing type & thing group

Gives every sensor a common type and makes it possible to query or bulk-manage "all brine tank sensors" later.

# run once
aws iot create-thing-type --thing-type-name BrineTankSensor
aws iot create-thing-group --thing-group-name brine-tank-sensors

1.2 — Production IoT policy

The policy every real device gets after provisioning. It uses ${iot:Connection.Thing.ThingName} so one device's certificate can never connect as, publish for, or read another device's topics — a compromised Pi only compromises itself. Topic pattern matches what the actual sensor-publish script (a02yyuw_iot.py) uses: pi/<thing-name>/telemetry — see the wifi & sensor image runbook for that script.

brine-tank-sensor-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "iot:Connect",
      "Resource": "arn:aws:iot:<region>:<account-id>:client/${iot:Connection.Thing.ThingName}"
    },
    {
      "Effect": "Allow",
      "Action": "iot:Publish",
      "Resource": "arn:aws:iot:<region>:<account-id>:topic/pi/${iot:Connection.Thing.ThingName}/telemetry"
    }
  ]
}
aws iot create-policy --policy-name BrineTankSensorPolicy \
  --policy-document file://brine-tank-sensor-policy.json

1.3 — IAM role that lets AWS IoT provision on your behalf

Fleet provisioning needs a role it assumes to create the Thing, certificate, and policy attachment for you. AWS ships a managed policy for exactly this. 

# trust-policy.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "iot.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
aws iam create-role --role-name BrineTankProvisioningRole \
  --assume-role-policy-document file://trust-policy.json

aws iam attach-role-policy --role-name BrineTankProvisioningRole \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSIoTThingsRegistration

1.4 — The provisioning template

This is the actual "recipe": given a SerialNumber parameter, create a Thing named after it, put it in the right group, and attach the production policy above.

provisioning-template.json
{
  "Parameters": {
    "SerialNumber": { "Type": "String" }
  },
  "Resources": {
    "thing": {
      "Type": "AWS::IoT::Thing",
      "Properties": {
        "ThingName": { "Fn::Join": ["", ["BrineTank-", { "Ref": "SerialNumber" }]] },
        "ThingTypeName": "BrineTankSensor",
        "ThingGroups": ["brine-tank-sensors"],
        "AttributePayload": { "version": "v1", "serialNumber": { "Ref": "SerialNumber" } }
      }
    },
    "certificate": {
      "Type": "AWS::IoT::Certificate",
      "Properties": {
        "CertificateId": { "Ref": "AWS::IoT::Certificate::Id" },
        "Status": "Active"
      }
    },
    "policy": {
      "Type": "AWS::IoT::Policy",
      "Properties": { "PolicyName": "BrineTankSensorPolicy" }
    }
  }
}
aws iot create-provisioning-template \
  --template-name BrineTankProvisioning \
  --provisioning-role-arn arn:aws:iam::<account-id>:role/BrineTankProvisioningRole \
  --template-body file://provisioning-template.json \
  --enabled

1.5 — Optional: validate the serial number before provisioning

A pre-provisioning hook is a Lambda AWS IoT calls before it honors a registration request — a natural fit since you already have Lambda in this pipeline. Check the serial number against an allow-list (a small DynamoDB table works fine) so a leaked claim certificate can't be used to register a device you never assigned an ID to. 

def lambda_handler(event, context):
    serial = event["parameters"].get("SerialNumber", "")
    allowed = serial in known_serials()  # e.g. a DynamoDB lookup
    return {"allowProvisioning": allowed}
aws iot create-provisioning-template \
  --template-name BrineTankProvisioning \
  --provisioning-role-arn arn:aws:iam::<account-id>:role/BrineTankProvisioningRole \
  --template-body file://provisioning-template.json \
  --pre-provisioning-hook targetArn=arn:aws:lambda:<region>:<account-id>:function:validate-new-brine-sensor \
  --enabled

1.6 — Let your laptop request claim certificates

The only new permission your own AWS credentials need: the ability to mint a five-minute claim certificate, scoped to this one template. 

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "iot:CreateProvisioningClaim",
    "Resource": "arn:aws:iot:<region>:<account-id>:provisioningtemplate/BrineTankProvisioning"
  }]
}
That's the whole one-time list. Everything below this point is what you'll actually repeat the next time you add a device.

2Per-device onboarding

The streamlined flow, end to end:

01
Flash & wire
Golden image on the SD card, sensor connected
02
Join wifi
Captive portal, at the tank — customer's whole part, done
03
Find its hostname
Router's DHCP client list — look for "brine-…"
04
Run one command
From your laptop, targeting the Pi by that hostname
05
5-min claim
Laptop mints a short-lived claim cert for this session only
06
Pi self-registers
Trades the claim for its own permanent cert + Thing
07
Timer starts
Confirm telemetry lands in the console/DB
Where the device gets its name. The Linux hostname is the one identifier used everywhere downstream (hostname → AWS IoT device ID → thing name → MQTT topic → whatever your Lambda keys the DynamoDB row on). Since the person setting this up at the tank may just be a customer who shouldn't need to touch SSH, the device names itself automatically on first boot, from its own CPU serial number (brine-<serial>) — no naming step for them at all. You look that name up afterward, from wherever you manage the fleet, to register it with AWS. Full details are in the wifi & sensor provisioning runbook.
  1. Flash the golden image and wire up the sensor

    Nothing to configure at flash time — Imager's Customisation isn't available for this custom image, and there's nothing it would need to set anyway. Full details in the wifi runbook linked above.

  2. Power it on and join the hotspot to configure wifi

    Join its hotspot and pick the real wifi network. That's the entire customer-facing setup — nothing else to do at the tank.

  3. Find the device's hostname

    Check your router's DHCP client list for the newest entry starting with brine- (e.g. brine-1000000012345678) — it already named itself, you're just looking it up. You can provision several devices around the same time now without conflict, since each one's name is unique from the moment it boots.

  4. Copy the onboarding scripts to your laptop (once)

    onboard-device.sh and onboard_device.py — download both, keep them side by side, and make the shell script executable.

  5. Run the onboarding script 
    ./onboard-device.sh pi@brine-1000000012345678.local

    No device-ID argument — it reads the hostname it finds over SSH, requests the claim certificate, runs the provisioning handshake, installs the resulting certificate, and starts the sensor timer — then wipes every trace of the temporary claim from both machines. Refuses to proceed if it sees the generic raspberrypi default, which would mean the device's own auto-naming failed (see the wifi runbook's troubleshooting).

  6. Watch for the confirmation line

    The script prints the AWS IoT thing name it was assigned, e.g. THING_NAME=BrineTank-brine-1000000012345678. That's your device's permanent identity going forward.

Adjust two constants before first use. Near the top of onboard-device.sh: REMOTE_CERT_DIR (where your sensor app expects its certificate files — matches the paths from the original tutorial you followed) and REMOTE_TIMER_NAME (the systemd timer that runs the sensor-reading app, so it can be started automatically once the new cert is in place).

3Verification checklist

  • Thing registered: aws iot describe-thing --thing-name BrineTank-<id> returns the expected thing type and group.
  • Certificate active: aws iot list-thing-principals --thing-name BrineTank-<id> shows exactly one certificate, and it's ACTIVE.
  • Telemetry flowing: subscribe to pi/+/telemetry in the MQTT test client, or check CloudWatch Logs for the Lambda invocation.
  • Database updated: confirm the expected row/record shows up for the new device.
  • Survives a reboot: the sensor systemd service is enabled, not just started.

4Retiring a device

Deactivate before you delete, so nothing can reconnect mid-cleanup:

aws iot update-certificate --certificate-id <cert-id> --new-status INACTIVE
aws iot detach-thing-principal --thing-name BrineTank-<id> --principal <certificate-arn>
aws iot detach-policy --policy-name BrineTankSensorPolicy --target <certificate-arn>
aws iot delete-certificate --certificate-id <cert-id>
aws iot delete-thing --thing-name BrineTank-<id>

5Security notes

  • Claim certs can't do anything else. They're only ever authorized for the two provisioning topics — never telemetry, never other devices' data.
  • Five-minute blast radius. If your laptop is compromised mid-onboarding, the exposure window for the claim credential is minutes, not the device's lifetime.
  • The pre-provisioning hook is your allow-list. Without it, anyone who obtains a claim certificate could register a device you never assigned an ID to. With it, only known serial numbers succeed.
  • Devices never hold IAM credentials. Only an X.509 certificate scoped to that one thing's topics — losing a Pi doesn't leak account access.
  • Treat the claim-issuing permission as sensitive. It's the one credential in this whole flow worth rotating and auditing — everything downstream of it is short-lived by design.

Appendix — codifying this in CDK

Since the rest of the stack (Lambda, tables) is already CDK, the one-time setup above can move into the same stack instead of living as a page of CLI commands — reviewable in git, deployed with everything else. Illustrative, not copy-paste complete: 

import * as iot from 'aws-cdk-lib/aws-iot';
import * as iam from 'aws-cdk-lib/aws-iam';

const provisioningRole = new iam.Role(this, 'BrineTankProvisioningRole', {
  assumedBy: new iam.ServicePrincipal('iot.amazonaws.com'),
  managedPolicies: [
    iam.ManagedPolicy.fromAwsManagedPolicyName('service-role/AWSIoTThingsRegistration'),
  ],
});

const sensorPolicy = new iot.CfnPolicy(this, 'BrineTankSensorPolicy', {
  policyName: 'BrineTankSensorPolicy',
  policyDocument: { /* same statements as section 1.2 */ },
});

new iot.CfnProvisioningTemplate(this, 'BrineTankProvisioningTemplate', {
  templateName: 'BrineTankProvisioning',
  provisioningRoleArn: provisioningRole.roleArn,
  enabled: true,
  templateBody: JSON.stringify({
    Parameters: { SerialNumber: { Type: 'String' } },
    Resources: {
      thing: { Type: 'AWS::IoT::Thing', Properties: {
        ThingName: { 'Fn::Join': ['', ['BrineTank-', { Ref: 'SerialNumber' }]] },
        ThingTypeName: 'BrineTankSensor',
        ThingGroups: ['brine-tank-sensors'],
        AttributePayload: { version: 'v1', serialNumber: { Ref: 'SerialNumber' } },
      }},
      certificate: { Type: 'AWS::IoT::Certificate', Properties: {
        CertificateId: { Ref: 'AWS::IoT::Certificate::Id' }, Status: 'Active',
      }},
      policy: { Type: 'AWS::IoT::Policy', Properties: { PolicyName: sensorPolicy.policyName } },
    },
  }),
});
