Golden Image: WiFi & Sensor Provisioning

Today, joining a new Pi to wifi means SSHing in over Ethernet or a keyboard/monitor to hand-edit network config. This runbook replaces that with a self-provisioning image: on first power-up, if the Pi doesn't recognize any wifi network, it broadcasts its own hotspot with a captive portal — connect with a phone, pick the real network, done. The same image already has the distance sensor driver installed and a scheduled job publishing readings to AWS IoT Core.

Companion to the AWS IoT device onboarding runbook — that one registers a device with AWS; this one gets it onto your network and reading the tank in the first place.

Overview

Three ways to get wifi credentials onto a headless Pi. Only one needs neither a screen nor a cable.

ApproachHow it worksFits you?
Manual (current) SSH in over Ethernet or a monitor/keyboard, edit network config by hand What you're doing now — needs physical access every time
Pre-seed credentials in the image Bake one wifi network's SSID/password into every SD card before flashing Breaks the moment the tank's router or password changes
Self-provisioning hotspot Device broadcasts its own AP + captive portal only when it has no known network to join This is what you asked for

The tool doing the actual work is comitup — purpose-built for exactly this: no known wifi → open an AP named comitup-<nnn> with a captive portal; join it from a phone or laptop, pick the real network, enter its password → comitup joins it, drops the AP, and remembers it for next time. It requires NetworkManager, which is why the target OS is Bookworm rather than an older release. Building a captive portal from scratch (hostapd + dnsmasq + a custom web form + per-OS captive-portal detection quirks) was considered and rejected — comitup already solves that reliably and is actively maintained.

What's in the image

# laid down by provision-image.sh comitup # wifi AP fallback + captive portal, NetworkManager-based /opt/brine-sensor/ DFRobot_RaspberryPi_A02YYUW/ # your existing sensor driver, unmodified a02yyuw_iot.py # your existing publish script, unmodified comitup-callback.sh # starts the sensor timer whenever wifi connects device.env # per-device config -- filled in during AWS onboarding set-hostname-from-serial.sh # names this device from its own CPU serial -- see below /etc/systemd/system/ brine-sensor.service # runs a02yyuw_iot.py once (oneshot), gated -- see below brine-sensor.timer # fires the service on a schedule -- replaces the crontab entry nightly-reboot.service # reboots the Pi -- see note below nightly-reboot.timer # fires it once a day, ~03:00 system time set-hostname-from-serial.service # runs the script above on every boot /etc/comitup.conf # external_callback = .../comitup-callback.sh

Your sensor driver and publish script are carried over exactly as they run today — nothing about how they read the sensor or talk to AWS IoT changed. A few things did change on the OS side: the cron entry became a systemd timer (same cadence, but now visible to systemctl status / journalctl instead of a silent cron log), the UART needs one-time configuration for the A02YYUW to be reachable at all (see the note below), and the device now reboots nightly.

Why the UART config matters. The A02YYUW driver opens /dev/ttyAMA0 directly. On a stock Pi, that device is claimed by Bluetooth, and the pins on the header are the secondary UART instead — so without this, the driver either can't open the port or reads from the wrong pins entirely. provision-image.sh sets dtoverlay=disable-bt so /dev/ttyAMA0 is the one wired to GPIO14/15, and turns off the login console on that UART so it isn't fighting the sensor for bytes.
Why the nightly reboot. In testing, the A02YYUW's readings drifted inaccurate after a few days of continuous uptime; rebooting nightly was the fix that worked, so it's baked into the image rather than left as a manual habit. nightly-reboot.timer fires /sbin/reboot around 03:00 in whatever timezone the Pi is set to (Raspberry Pi OS defaults to UTC unless you set one) — check with timedatectl if you want it landing at 3am your local time specifically, and adjust OnCalendar= in the timer unit if you'd rather it fire at a different hour.

Naming a device: automatic, from its own hardware — no customer step

The device's hostname is the one identifier used everywhere downstream: it becomes the AWS IoT device ID, the AWS IoT thing name, the MQTT topic, and — since telemetry is written to DynamoDB keyed on it — the partition key on every row it produces. Since a customer setting this up shouldn't have to invent a name (or touch SSH at all), each device names itself: on every boot, set-hostname-from-serial.service reads this specific Pi's unique CPU serial number out of /proc/cpuinfo — burned into the hardware at manufacture, so it's guaranteed different on every board even though every device runs the exact same golden.img — and sets the hostname to brine-<that serial> (e.g. brine-1000000012345678). It's idempotent (a no-op once the hostname already matches), so it's safe to enable unconditionally on every boot rather than gating it on "first boot only."

The customer's entire interaction is picking a wifi network and entering its password — nothing about naming ever surfaces to them. On your side, this means you don't type a hostname in either; instead you look one up when it's time to register the device with AWS (see Phase B below).

Two things this deliberately doesn't do. It doesn't try to patch Raspberry Pi Imager's own Customisation step back to life for custom images — that's disabled upstream and out of our control. And it doesn't build a custom captive-portal naming page (an earlier design this runbook used did exactly that) — that would mean patching comitup's own web templates or hosting a second page the customer has to know to look for, for a problem the hardware serial already solves with zero UI at all. comitup's external_callback hook is still used, just for something smaller: making sure the sensor timer is running whenever wifi connects.
Want a friendlier name for your own SSH use? Nothing stops you from renaming a device later with sudo raspi-config nonint do_hostname <name> for your own convenience — just know that's purely local. The AWS identity (thing name, DynamoDB key) is fixed to whatever hostname existed at the moment you ran onboard-device.sh; renaming the Pi afterward doesn't change what's already in AWS.
Do once

ABuild the golden image

You do this once, on one reference Pi, to produce a golden.img file you'll reuse for every future device.

Target hardware: Raspberry Pi Zero 2 W. Cheapest board that does the job — but it has no Ethernet jack, only onboard wifi (plus a USB OTG data port). The steps below get the one-time build run online without one.
  1. Flash Raspberry Pi OS Bookworm Lite (64-bit)

    Use Raspberry Pi Imager. In the Customisation step: set a hostname (anything's fine for this reference Pi — sanitize-for-imaging.sh resets it before capture anyway), enable SSH (key-based is fine), set a username/password — and this one time only, also fill in Configure wireless LAN with your real home network. This reference Pi needs internet access to install packages; devices flashed from the finished image never will, and sanitize-for-imaging.sh (step 5) wipes this network back out before you capture the image, so it never ships in golden.img.

  2. Boot it and SSH in over your home wifi

    No cable needed. Find its address from your router's client list, or ping <hostname>.local from your laptop.

  3. Copy over and run the provisioning script 
    scp provision-image.sh pi@<ip>:~
ssh pi@<ip>
sudo TARGET_USER=pi ./provision-image.sh

    Installs comitup, fixes the UART, deploys the driver + publish script (embedded in the script itself, nothing to git clone), and installs the systemd timer — enabled but not yet started, since device.env still has placeholder values.

  4. Verify comitup, then verify the sensor

    See the verification checklist below — do this before capturing the image, not after, or you'll be debugging blind on every future device.

  5. Sanitize, then power off 
    sudo ./sanitize-for-imaging.sh
sudo poweroff

    Strips SSH host keys, the machine-id, your build-time home wifi credential from step 1, any other networks comitup learned during testing, and any test AWS certificate — so devices cloned from this image don't all share one identity, and none of them ship with your real wifi password.

  6. Capture the SD card as golden.img

    On Windows: Win32 Disk Imager → Read → point it at the SD card → save as golden.img. Optional: shrink the result with PiShrink (needs a Linux environment — WSL works) so the file isn't the full card size before you archive it.

Would rather not type your real wifi password into Imager, even temporarily? The Zero 2 W's USB data port (labeled USB, not PWR) supports OTG gadget networking: add dtoverlay=dwc2 to config.txt and modules-load=dwc2,g_ether to cmdline.txt on the boot partition before first boot, then plug that single USB port straight into your laptop with a data-capable cable. The Pi shows up as a USB Ethernet device; share your laptop's internet connection to it (Windows: adapter Properties → Sharing tab) and SSH in over that link instead. More fiddly to set up than step 1, but no wifi credential ever touches the reference Pi.
Don't skip sanitizing. Skipping it means every device you ever flash from this image starts with the same SSH host keys and the same machine-id — harmless until it very much isn't (SSH host-key warnings, DHCP/mDNS collisions between devices).

Steps 1–4 are the entire customer-facing setup — flash the card, plug it in, join a hotspot, pick a wifi network. Steps 5–6 are yours, done afterward from wherever you manage the fleet; the customer never needs to be involved in them or even know they happen.

  1. Flash golden.img to a new SD card

    Raspberry Pi Imager → Choose OS → Use custom → select golden.img. There's no Customisation step to fill in — it's unavailable for a local image file — and nothing to fill in even if it were: SSH, the pi login, and the device's own hostname are all already handled by the image itself.

  2. Install it at the tank and power it on

    No cables needed beyond power and the sensor's own wiring.

  3. Join the hotspot and configure wifi

    On a phone: connect to comitup-<nnn> (no password). A captive portal should open automatically; if it doesn't, browse to http://10.42.0.1 or http://comitup-<nnn>.local. Pick the real network, enter its password. The device joins it and the hotspot disappears within about 30 seconds — your phone will typically reconnect to that same real network on its own a moment later. That's the whole customer-facing setup, done.

  4. Find the device's hostname

    It already named itself on first boot — you just need to look it up. Check your router's DHCP client list for the newest entry starting with brine- (e.g. brine-1000000012345678). Multiple devices can be provisioned around the same time now without conflict, since each one's name is unique from the moment it boots — no more "one at a time" constraint.

  5. Register the device with AWS IoT Core

    From your laptop, using the hostname you just looked up:

    ./onboard-device.sh pi@brine-1000000012345678.local

    The script reads that hostname over SSH and uses it as the device's AWS IoT identity — refusing to proceed if it sees the generic raspberrypi default, which would mean something's actually wrong (see Troubleshooting) rather than a step you forgot — then writes it into device.env and starts the sensor timer, so this one command finishes the job end to end.

Verification checklist

Comitup / wifi

  • Service running: systemctl status comitup shows active.
  • AP appears with no known network: a phone nearby sees comitup-<nnn> in its wifi list.
  • Captive portal loads and lists nearby networks to choose from.
  • After submitting credentials, the AP disappears and the device is reachable on the real network (check your router's client list, or ping <hostname>.local).
  • Power-cycle test: reboot the device while it's on real wifi — it should reconnect to that network directly, no AP.

Sensor + publish

  • UART is free: ls -l /dev/ttyAMA0 exists; systemctl status serial-getty@ttyAMA0 shows masked/inactive.
  • Manual read works: sudo systemctl start brine-sensor.service && journalctl -u brine-sensor.service -n 20 shows real distance readings, not status errors (this bypasses the ExecCondition gate, so it works even before onboarding).
  • Timer is scheduled: systemctl list-timers brine-sensor.timer shows a next-run time once the device is onboarded.
  • Telemetry lands in AWS: confirmed via the AWS onboarding runbook's own checklist.
  • Nightly reboot is scheduled: systemctl list-timers nightly-reboot.timer shows a next-run time (it's unconditional, so this should show up immediately, unlike the sensor timer).

Auto-hostname

  • Hostname is set correctly: hostname on the device returns brine-<its CPU serial>, not raspberrypi — compare against awk -F': ' '/^Serial/{print $2}' /proc/cpuinfo.
  • Service ran cleanly: systemctl status set-hostname-from-serial.service shows active (exited), not failed.
  • Reboot test: power-cycle the device — the hostname should come back identical (deterministic from hardware, not randomly regenerated).
  • Two devices, two names: if you have more than one reference build or test device, confirm they get different hostnames from each other.

Troubleshooting

  • No AP shows up at all: journalctl -u comitup for errors; confirm nmcli device status shows wlan0 managed by NetworkManager, not unmanaged.
  • Captive portal doesn't auto-open on the phone: normal on some OS/browser combinations — browse to http://10.42.0.1 directly.
  • Sensor timer doesn't start right after wifi connects: check journalctl -t comitup-callback for what the callback saw, and confirm external_callback is actually set in /etc/comitup.conf.
  • Sensor reads come back with a nonzero status: almost always wiring or the UART overlay — re-check dtoverlay=disable-bt is in /boot/firmware/config.txt and that nothing else has /dev/ttyAMA0 open (sudo fuser /dev/ttyAMA0).
  • Timer never fires: check that device.pem.crt exists in the cert directory — the ExecCondition gate on brine-sensor.service is waiting on it, meaning onboard-device.sh hasn't run (or didn't finish) yet.
  • Device still shows the generic raspberrypi hostname: means set-hostname-from-serial.service genuinely failed — check journalctl -u set-hostname-from-serial.service on the device. The most likely cause is /proc/cpuinfo not exposing a Serial line (unusual on real Raspberry Pi hardware); the fallback is to set one by hand with sudo raspi-config nonint do_hostname <name> and reboot.
  • Can't find a device's hostname in the router's client list: give it a minute after step 3 — the router needs to pick up the new DHCP lease and its hostname before it shows up. If it's still missing, confirm the device actually left the comitup-<nnn> hotspot (check the router's list for that name too, or that the hotspot itself is gone).

Security notes

  • The fallback AP is open (no password) by design — that's how you get in to configure it. It only exists while the device has no known network, and only within wifi range, so the exposure window is physical proximity plus "not yet configured."
  • Every device gets its own SSH host keys and machine-id once sanitize-for-imaging.sh has run before capture — don't skip it.
  • No AWS credentials are baked into the image. The image only knows how to reach the sensor and AWS's public endpoint; the device-specific certificate arrives later via onboard-device.sh, same short-lived-claim model as the AWS onboarding runbook.
